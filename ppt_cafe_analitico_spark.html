El Muro de la RAM

Mentalidad "Single Node"

Pandas / Excel / Laptop

  • Todo el dato debe caber en TU memoria RAM.
  • Si el dato crece, tu código falla (OOM).
  • Procesamiento secuencial (1 fila a la vez).

Mentalidad "Distribuida"

Apache Spark

  • El dato es más grande que la RAM de una máquina.
  • Divide y Vencerás: Romper el problema en trozos pequeños.
  • Si el dato crece, agregas más máquinas.

La Orquesta (Arquitectura)

El Driver (El Director)

Es tu notebook. Contiene tu código.

Crea el plan de ejecución.

NO toca los datos pesados.

Los Executors (Los Músicos)

Viven en los nodos del cluster.

Ejecutan las tareas en paralelo.

Tienen los datos en su RAM.

El Superpoder: "Ser Perezoso"

Eager (Ansioso)

Pandas / Python Nativo


df = read_csv("data.csv") # ¡LEE YA!
df = df.filter(col > 5)   # ¡FILTRA YA!

Ineficiente: Lee todo para luego tirar la mitad.

Lazy (Perezoso)

Spark


df = read("data")   # "Anotado."
df = df.filter(...) # "Anotado."
df.write(...)       # ¡ACCIÓN!

Inteligente: Solo lee lo que necesita al final.

Tu Copiloto Invisible: Catalyst

¿Qué pasa cuando ejecutas código?

Spark no ejecuta tu código línea por línea ciegamente. Lo reescribe.

  • Predicate Pushdown: Si filtras por fecha al final, Spark mueve ese filtro al principio para leer menos datos.
  • Column Pruning: Si solo usas 2 columnas, Spark ignora las otras 100 desde el disco.

"Tú dices QUÉ quieres.
Catalyst decide CÓMO hacerlo."

El Enemigo: El Shuffle

¿Por qué mi Job es lento?

El 90% de las veces es por mover datos a través de la red.

Operaciones que causan Shuffle:

  • GROUP BY
  • JOIN
  • DISTINCT
  • ORDER BY

Consejo: Filtra (reduce datos) ANTES de hacer Join.

La Regla de Oro: Particionamiento

1 Partición
1 Core (CPU)
1 Task

Si tienes un cluster de 100 cores pero tu dataframe tiene 1 partición...
99 cores estarán de vacaciones.

El Asesino Silencioso: Data Skew

¿Qué es el Skew?

Cuando una partición es mucho más grande que las demás.

Síntoma: El job llega al 99% y se queda ahí por horas.

Ejemplo Clásico

Hacer GROUP BY country y el 90% de tus usuarios son de "US".

Un solo core procesará "US" mientras los demás terminan en segundos.

¡Lento!

Tiempos de Ejecución por Task

Funciones: Lo Bueno, Lo Malo y Lo Feo

1. Spark Native

Recomendado


import pyspark.sql.functions as F
df.withColumn("upper", F.upper(col("s")))
  • Ejecuta en JVM (Rápido).
  • Catalyst lo optimiza.
  • Sin serialización Python.

2. Pandas UDF

Aceptable


@pandas_udf("string")
def upper_udf(s: pd.Series):
    return s.str.upper()
  • Usa Apache Arrow.
  • Vectorizado (Batch).
  • Bueno para ML.

3. Python UDF

Evitar


@udf("string")
def upper_udf(s):
    return s.upper()
  • Fila por fila (Lento).
  • Serialización costosa.
  • Caja negra.
Nuevo Paradigma

Spark en la Era de Gen AI

Spark no es solo para tablas SQL. Es el motor de pre-procesamiento para LLMs.

  • Batch Inference:
    Pasar 1 millón de prompts a un modelo (vía `pandas_udf`).
  • RAG Data Prep:
    Leer PDFs masivos, chunking y tokenización en paralelo antes de enviar a Vector DB.

Ejemplo: Inferencia Masiva


@pandas_udf("string")
def predecir_batch(textos: pd.Series) -> pd.Series:
    # Carga el modelo UNA vez por Executor
    model = load_model() 
    return textos.apply(model.predict)

# Spark distribuye los textos en batches
df.withColumn("prediccion", predecir_batch("texto"))

Los 3 Pecados Capitales

1. .collect()

Intentar traer 100GB a la RAM de tu driver.

Consecuencia: Driver OOM Crash.

2. Bucles `for`

Iterar filas con Python nativo.

Consecuencia: No usas Spark, usas Python lento.

3. UDFs Innecesarias

Escribir funciones Python para cosas que Spark ya sabe hacer.

Consecuencia: Caja negra para Catalyst.
