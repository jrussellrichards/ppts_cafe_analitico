Anatomía de un Cluster: Driver → Executors → Tasks

1

Driver (Cerebro)

Orquesta todo. Crea el DAG, lo optimiza con Catalyst, y divide el trabajo en Tasks.

Vive en tu notebook de Databricks

2

Executors (Trabajadores)

Procesos JVM distribuidos en el cluster. Cada uno tiene N cores y RAM asignada.

Ej: 4 executors × 8 cores cada uno = 32 cores totales

3

Tasks (Unidad Atómica)

Cada Task procesa UNA partición en UN core. Si tienes 32 cores y 100 particiones, se ejecutan 32 Tasks en paralelo, luego otras 32, hasta completar las 100.

1 Partición = 1 Task = 1 Core (en un momento dado)

El Vocabulario de Spark: Transformaciones vs. Acciones

🗺️

Transformaciones

Instrucciones (Lazy)
Son promesas de cálculo. Crean un nuevo DataFrame a partir del anterior.

.select()
.filter()
.groupBy()
.withColumn()
🚀

Acciones

Ejecución (Eager)
Disparan el trabajo real. Devuelven un resultado al driver o escriben a disco.

.count()
.show()
.write()
.collect()

Insight: Spark no mueve un dedo hasta que ve una Acción.

Script del Orador:
"Ya sabemos que tenemos un Driver y muchos Executors. Pero, ¿cómo le dice el Driver a los Executors qué hacer? No usamos bucles for. Usamos un vocabulario específico dividido en dos mundos: Transformaciones (planos) y Acciones (gatillos). El Driver no mueve un dedo hasta ver una Acción."

Tipos de Transformaciones: Narrow vs Wide

🔗

Narrow Transformations

1:1 Dependency

Definición:

Cada partición de entrada genera exactamente una partición de salida. Los datos permanecen en el mismo nodo. 

# Ejemplos de Narrow Transformations
df.filter(col("edad") > 18)
df.select("nombre", "ciudad")
df.withColumn("nuevo", col("viejo") * 2)
df.map(lambda x: x.upper())
✓ Procesamiento local
✓ Pipeline optimizable
✓ Sin transferencia de red
🌐

Wide Transformations

N:N Dependency

Definición:

Cada partición de salida puede depender de múltiples particiones de entrada. Requiere reorganizar datos entre nodos. 

# Ejemplos de Wide Transformations
df.groupBy("categoria").count()
df.orderBy("fecha")
df1.join(df2, "id")
df.distinct()
⚠ Shuffle de datos (costoso)
⚠ Uso intensivo de red
⚠ Nueva etapa (stage boundary)
💡 Clave: Wide = Shuffle = Punto de Sincronización
Script del Orador:
"Antes de hablar de shuffle, necesitan entender esta distinción fundamental. Narrow Transformations: Una partición de entrada produce una partición de salida. Es como procesar una hoja de Excel: todo se queda local. Filter, select, withColumn... todo es narrow. Wide Transformations: Aquí es donde la cosa se pone interesante. Para hacer un groupBy por 'ciudad', necesito reunir TODAS las filas de 'Madrid' que están repartidas en diferentes máquinas. Eso significa mover datos por la red. Esta diferencia es crítica porque las Wide Transformations crean 'stage boundaries' - puntos donde Spark tiene que parar, barajar datos, y empezar una nueva etapa de procesamiento. Narrow = pipeline eficiente. Wide = checkpoint costoso."

El Secreto del Rendimiento: Shuffle vs No Shuffle

✅

Sin Shuffle

Narrow Transformation

# Cada partición se procesa LOCALMENTE
df_filtered = df.filter(col("monto") > 1000)

# También: .select(), .withColumn(), .map()

⚡ Rápido: Los datos NO se mueven entre nodos

⚠️

Con Shuffle

Wide Transformation

# Datos se REDISTRIBUYEN por clave
df_grouped = df.groupBy("ciudad").count()

# También: .join(), .repartition(), .distinct()

🐢 Costoso: Transferencia masiva por red entre nodos

Regla de Oro: Minimiza los shuffles = Maximiza el rendimiento
Script del Orador:
"Aquí está el secreto que separa a los que escriben código lento de los que escriben código rápido. A la izquierda: operaciones SIN shuffle. Cada executor procesa sus datos localmente, sin hablar con nadie. A la derecha: operaciones CON shuffle. Los datos tienen que viajar por la red para reagruparse. Un groupBy puede mover terabytes entre máquinas. Un filter no mueve nada. ¿La regla de oro? Filtra ANTES de agrupar. Reduce datos ANTES del shuffle. Esto puede ser la diferencia entre un job de 5 minutos y uno de 5 horas."

Lazy Evaluation

# 1. Leer datos
df = spark.table("ventas")

# 2. Filtrar
df_filtrado = df.filter(col("monto") > 1000)

Script del Orador:
"La teoría suena genial. Pero en la práctica, esa 'pereza' y el modelo distribuido pueden ser trampas mortales. Challenge #1: Will it CRASH? Miren este código..."
💥 CRASH

❌ Driver Out of Memory (OOM)

Error típico:
java.lang.OutOfMemoryError: GC overhead limit exceeded

¿Por qué explota?

  • .toPandas() ejecuta el job distribuido y trae TODOS los resultados al driver
  • El driver típico en Databricks tiene 8-16 GB de RAM
  • 2-3 millones de filas filtradas = 3-5 GB en memoria (sin compresión)
  • Boom 💥 – OOM, cluster cuelga, perdiste 10 minutos de cómputo

✅ La solución correcta: 

# Opción 1: Toma solo una muestra
sample_df = df_filtered.limit(10000).toPandas()

# Opción 2: Agrega primero, luego trae
agg_df = df_filtered.groupBy("fecha").agg(sum("monto")).toPandas()

# Opción 3: Guarda y visualiza en Databricks (sin Pandas)
df_filtered.write.format("delta").save("/results")
display(df_filtered)  # Databricks native viz

Regla de oro: Nunca traigas millones de filas al driver. Agrega primero, muestra después.

Script del Orador:
"¡CRASH! Si levantaron la mano, bien hecho. El problema no fue el filtro, fue la ACCIÓN .toPandas(). Intentaron traer el océano a un vaso de agua (el Driver). Jamás hagan esto con Big Data."

df = spark.table("ventas_10M")

    (col("precio") / 0).alias("precio_normalizado")  # ← 🚨 División por cero

¿Qué pasará? 🤔

Script del Orador:
"Aprendimos que las acciones masivas matan el Driver. Ahora, ¿qué pasa con los errores de lógica pura? Challenge #2: División por cero. ¿Explota o no explota?"
✓ SAFE

✅ No explota... todavía

Output real:
Pipeline construido exitosamente ✓

¿Por qué no explota?

  • Lazy Evaluation: Spark solo construye el DAG, NO ejecuta cálculos
  • El error (/ 0) existe en el plan lógico, pero nunca se evalúa
  • Sin acción (.count(), .show(), .write()), no hay ejecución
  • El mensaje "✓" se imprime porque Python ejecutó sin problemas – Spark no hizo nada aún

⚠️ Pero si agregamos una acción... 

df_filtered.show()  # ← AQUÍ explota
# ArithmeticException: Division by zero

💡 La Lección Clave:

En Pandas, los errores explotan cuando defines la transformación. En Spark, explotan cuando ejecutas la acción. Esto significa que puedes tener pipelines enteros con bugs latentes que solo descubes en producción cuando los datos reales activan la acción.

Pro tip: Usa df.explain() para ver el plan sin ejecutarlo

Script del Orador:
"¡SAFE! No explota... todavía. ¿Por qué? Porque Spark es Lazy. El error está en el plan, pero sin una Acción, el plan no se ejecuta. El error está latente, esperando a producción."

Tiempo estimado en cluster de 32 cores:

¿Por qué es tan lento?

💀 El Anti-Pattern: "Pandas en Spark"

Este código convierte Spark en una versión CARA y LENTA de Pandas. Estás pagando por un cluster de 32 cores, pero solo usas 1. Es como rentar un Ferrari para manejar en primera velocidad.

df_resultado = (df
    .filter(col("monto") > 1000)

        ((col("ganancia") / col("monto")) * 100).alias("margen")

)

Particiones: La Clave para 10M de Registros

❌ El Error Común: Over-Partitioning

1

3
4
5

7
8
...
...
...
...
...
...
2000
2000 particiones × 10,000 rows cada una

Problema: Cada Task tiene overhead (scheduling, serialización). Si una partición tiene solo 5,000 filas, el overhead de gestión es mayor que el procesamiento real.

Resultado: Job lento debido a task overhead, no a procesamiento de datos.

✓ La Regla de Oro para 10M Registros

Particiones = Cores × 2 a 4

Si tienes 32 cores → 64 a 128 particiones

df = spark.table("data")
  .repartition(128) # Explicit

# O configura globalmente:
spark.conf.set(
  "spark.sql.shuffle.partitions",
  128
)

Resultado: Cada partición tiene ~78K-156K filas. Balance perfecto entre paralelismo y overhead.

⚡ Bonus: Evitar Shuffles Innecesarios

Operaciones que causan Shuffle:

  • groupBy(), join(), distinct()
  • repartition(), coalesce() (con aumento)
  • orderBy() global

Estrategia de Optimización:

  • Filtrar ANTES de join (reduce datos a mover)
  • Usar broadcast() para tablas < 10MB
  • Particionar por clave de join si es recurrente

Almacenamiento: Row-Oriented vs Columnar

Row-Oriented (CSV, Teradata)

Row1: [id, nombre, edad, ciudad, ...20 cols]
Row2: [id, nombre, edad, ciudad, ...20 cols]
Row3: [id, nombre, edad, ciudad, ...20 cols]
  • –Lee registros completos
  • –Bueno para: OLTP, transacciones
  • –Malo para: Analytics (lees datos innecesarios)

SELECT edad FROM tabla
❌ Lee las 20 columnas

Columnar (Parquet)

Col_id: [1, 2, 3, 4, ...]
Col_edad: [25, 30, 45, 22, ...]
Col_ciudad: ["NY", "LA", ...]
  • –Lee solo las columnas necesarias
  • –Bueno para: Analytics, Agregaciones
  • –Compresión brutal (valores repetidos)

SELECT edad FROM tabla
✓ Lee SOLO la columna 'edad' (Projection Pushdown)

Insight: Con 20 columnas, Parquet puede ser 20x más rápido que CSV para queries analíticas.

⏱️

El Problema

Inferencia secuencial en Pandas:

10ms × 10M filas
= 27 Horas

Un solo core procesando
todo secuencialmente

⚡

La Solución: Pandas UDF

Envuelve tu función de Python con @pandas_udf

  • ✓Paraleliza tu código de LangChain/HuggingFace
  • ✓Spark distribuye batches a todos los cores
  • ✓Cada executor procesa su partición
  • ✓Mismo código Python, 100x más rápido
27 horas → 15 minutos

💻 Código: Vectorizar Texto 

from pyspark.sql.functions import pandas_udf
from sentence_transformers import SentenceTransformer

# Tu función Python normal
@pandas_udf("array<float>")
def vectorize_text(texts: pd.Series) -> pd.Series:
    model = SentenceTransformer('all-MiniLM-L6-v2')
    embeddings = model.encode(texts.tolist())
    return pd.Series(embeddings.tolist())

# Spark la distribuye en paralelo
df_vectorized = df.withColumn(
    "embedding",
    vectorize_text(col("documento"))
)

Casos de uso:
• Embeddings para RAG (50K PDFs)
• Sentiment Analysis (10M chats)
• Tokenización con spaCy/NLTK
• Inferencia de modelos ML

Checklist: Spark Eficiente para 10M Registros

✓ Formato de Datos

  • Siempre usar Parquet (o Delta Lake)
  • Particionar por columnas de filtrado frecuente
  • Evitar CSV en producción

✓ Particiones

  • Configurar shuffle.partitions = cores × 2-4
  • ~100K-200K filas por partición (ideal)
  • Usar .coalesce() al escribir resultados pequeños

✓ Transformaciones

  • Pensar declarativo, NO iterativo
  • Filtrar lo antes posible en el pipeline
  • Usar funciones nativas de Spark (no UDFs Python)

✓ Joins & Shuffles

  • Broadcast joins para tablas < 10MB
  • Reducir datos antes de join
  • Pre-particionar datos recurrentes
Spark Eficiente = Formato Correcto + Particiones Balanceadas + Lazy Thinking
